# КОБОЛЬТ-Б

Конструктор внутреннего боевого листка танкового батальона.
Next.js (App Router) + TypeScript + Tailwind CSS.

## Статус: шаг 2 вертикального слайса (визуальная обложка)

Шаг 1 (репозиторий, модель Issue, IndexedDB, создание выпуска) —
готов, без изменений.

Шаг 2 добавляет:
- `components/canvas/PageFrame.tsx` — физический размер страницы
  (210×297mm) в одном месте;
- `components/canvas/A4Page.tsx` — единая точка входа для отображения
  страницы выпуска; и Preview, и будущий `/api/pdf` (шаг 5) рендерят
  именно её, без отдельной вёрстки для печати;
- `components/canvas/PagePreviewScaler.tsx` — вписывает физическую
  страницу в ширину экрана (масштабирование только визуальное, сама
  PageFrame остаётся в мм);
- шаблон обложки `cover-v1` (`components/templates/cover/`),
  разложенный на компоненты: `Masthead`, `IssueMeta`, `Emblem`,
  `HeroMedia`, `ContentsBlock`, `EditorialRule`. `CoverV1.tsx` их
  просто собирает и передаёт данные из `Issue` — вёрстки внутри себя
  не содержит;
- `components/decorative/EngravingTank.tsx` — авторская линейная
  гравюрная иллюстрация (фон/водяной знак), не копия референсных фото;
- реальные кириллические шрифты (Oswald + PT Sans) через
  `next/font/google` — скачиваются один раз при сборке и хостятся как
  статика приложения (self-hosted), без обращений к Google Fonts в
  рантайме — одинаково работает в Preview и в headless Chromium на
  шаге PDF;
- `/issues/[issueId]/preview` — базовый preview обложки;
- кнопка "Заполнить демо-контентом" на странице выпуска — только для
  визуальной проверки шаблона, не часть системы шаблонов и не
  запускается автоматически.

Дизайн-принцип, зашитый в компоненты: `ContentsBlock` и `HeroMedia`
показывают ровно то, что есть в `Issue` — без выдуманного текста;
если материала мало, остаётся пустое пространство (плюс фоновая
гравюра как композиционный якорь), а не placeholder-заполнение.

  текст в две колонки;
- `lib/content/pageBlocks.ts` — общая группировка ContentBlock на
  заголовок/подзаголовок/абзацы/фото/цитаты для обоих шаблонов;
- `EditorialRule` вынесен в `components/shared/` (используется и
  обложкой, и внутренними страницами);
- `/qa/page2` — Template A и Template B на трёх объёмах контента
  (`lib/content/qaFixturesPage2.ts`) для визуальной регрессии.

QA дал два findings, оба исправлены до сдачи:
1. Template B при единственном абзаце: фиксированная раскладка в 2
   колонки текста оставляла одну колонку пустой и текст выглядел
   перекошенным — колонки теперь включаются только при 2+ абзацах.
2. Template B при 5 фотографиях + большом объёме текста: сетка фото
   считала высоту миниатюры фиксированной (58мм) независимо от числа
   строк, из-за чего страница переполнялась примерно на 12мм за
   пределы A4 (ContentBlock обрезался `overflow:hidden` PageFrame).
   Высота миниатюры теперь уменьшается по числу строк сетки в рамках
   фиксированного бюджета высоты — проверено программным замером
   `scrollHeight` относительно `clientHeight` страницы, переполнение
   устранено (0мм на всех шести проверенных состояниях).

Решение по автомасштаблированию (принято, не реализовано): при
переполнении контента страница НЕ должна ломаться, обрезаться или
уменьшать шрифт до нечитаемого размера. Целевое поведение — состояние
"Материала слишком много для выбранного шаблона. Выберите другой
шаблон или сократите материал". Сам механизм намеренно отложен.

Шаблоны:

раскладка не ломается ни в одном случае.

Сознательно НЕ реализовано:

  в будущем — предупреждение «Материала слишком много для выбранного

  механизм по-прежнему отложен;

Это чисто проверочный шаг: новых шаблонов и правок дизайна нет. Ни

Проверено (программно + визуально):
- **overflow** — вертикальный и горизонтальный, на всех 8 страницах
  (2 выпуска × 4 страницы): 0мм реального переполнения везде;
- **"В номере"** на обложке обоих выпусков подтягивает заголовки и

  дублирования данных — включая случай, когда миниатюр ещё нет
  (минимальный выпуск);
- **нумерация** — `InnerHeader` каждой страницы показывает верный
  номер (02/03/04), автоматически из `pageNumber`;
- **единство дизайна при разных композициях** — поля, шапка, палитра,
  типографика, линии и гравюрные элементы совпадают на всех 4
  страницах обоих выпусков, но композиция каждой страницы разная
  (проверялось визуально бок о бок);
- **правило "без фото — без заглушки"** подтверждено в контексте
  полного выпуска: на странице 4 минимального выпуска фото нет и
  заглушки нет, при том что страницы 2–3 того же выпуска корректно

При подготовке этой проверки была найдена и исправлена одна ошибка —

## Статус: шаг 7 (редактор выпуска)

**Принцип EDITOR DATA → Issue JSON → A4Page → Preview выдержан
буквально**: редактор (`app/issues/[issueId]/page.tsx`) не рисует
ничего сам — все формы пишут в объект `Issue` через `persist()`
(state + `updateIssue` в IndexedDB), а Preview рендерит тот же
`A4Page`, что и everywhere в приложении. Отдельной "версии дизайна для
редактора" нет ни в коде, ни по архитектуре.

Новое:
- **Dashboard** (`/`) переписан: номер/дата/дата изменения/кнопки
  "Открыть"/"Удалить" по каждому выпуску, подтверждение перед
  удалением, аккуратное пустое состояние. Количество страниц не
  варьируется — по ТЗ выпуск всегда состоит ровно из 4 страниц.
- **Страница редактора** (`/issues/[issueId]`) — верхняя панель
  (номер/дата/"Сохранено ✓"), слева `PageList` + `TemplatePicker` +
  форма контента, справа `A4Page` в `PagePreviewScaler` (масштабируется
  целиком, пропорция A4 не нарушается). На узких экранах сайдбар
  переходит из колонки в строку выше превью (`lg:flex-row`).
- **`lib/content/sections.ts`** — редакторская модель `PageSections`
  (заголовок/подзаголовок/абзацы/фото/цитата/достижения) и её
  конвертация в `ContentBlock[]` и обратно. Именно она делает
  "смена шаблона не удаляет контент" реальной, а не только
  архитектурно заявленной: `TemplatePicker` меняет только
  `templateId`, `PageContent` не трогается вообще.
- **`lib/content/templateOptions.ts`** — реестр доступных шаблонов по
  номеру страницы (ровно те id, что зафиксированы в шаге 7, п.4) и
  конфигурация фото-редактора (максимум кадров, нужны ли поля
  имя/должность) для каждого шаблона.
- **Редактор обложки** (`CoverForm`) — номер, дата, hero-заголовок,
  подзаголовок, фото (одно, с подписью), цитата с автором. Постоянные
  элементы (название издания, слоган, эмблемы, гравюра) — не поля
  формы, как и требовалось.
- **Текстовые блоки страниц 2–4** (`InnerPageForm` +
  `ParagraphsEditor`/`PhotosEditor`/`QuoteEditor`/
  `AchievementsEditor`): добавить/удалить/изменить абзац, изменить
  порядок (кнопки вверх/вниз), добавить/удалить/заменить фото с
  подписью (плюс имя/должность на странице 4 — редактор не
  подставляет заглушку при удалении фото, шаблон и так не рисует её),
  список достижений — только для `team-faces-v1`, цитата —
  добавить/изменить/удалить. Последняя строка задания (п.6) обрывалась
  на полуслове — доделал по контексту раздела; если там подразумевалось

Небольшое расширение дизайн-системы, потребовавшееand для поля

## Архитектура PDF (согласовано, реализация — на шаге 5)

Клиент сериализует весь `Issue` (JSON, включая base64/data-URL фото) и
отправляет его целиком в `POST /api/pdf`. Сервер не обращается к
IndexedDB — он ничего не знает о выпуске, кроме присланного тела
запроса. Роут рендерит **тот же** React-компонент `A4Page`, что и
Preview в браузере (через headless Chromium), — разметка не
дублируется. Для запуска Chromium в serverless-функции Vercel
используется `puppeteer-core` + `@sparticuz/chromium` (обычный полный
`puppeteer` превышает лимит размера serverless-функции на Vercel);
альтернатива при необходимости — вынести рендер в отдельный сервис
(например, Browserless) и обращаться к нему по HTTP из `/api/pdf`,
если потребуется больше 50 сек. на функцию.

## Runtime QA

Этот проект требует **сети** (npm registry) и **Chromium** (для
Playwright), которых нет в среде, где готовился этот код. Ниже —
единственный подтверждённый способ провести реальную runtime-проверку.

### Install

```bash
npm install
```

`package-lock.json` в репозитории намеренно отсутствует — он должен
быть сгенерирован здесь, на машине/CI с доступом к registry. Ручной,
"нарисованный" lockfile не создавался: `npm ci` в CI-workflow
(`.github/workflows/qa.yml`) будет падать до тех пор, пока
получившийся `package-lock.json` не закоммичен в репозиторий.

### Development

```bash
npm run dev
```

### Runtime tests

```bash
npm run qa:runtime
```

Запускает `qa/runtime/*.spec.ts` через Playwright на трёх вьюпортах
(1440×900, 1024×768, 390×844 — см. `playwright.config.ts`), с
`webServer`, который сам поднимает `npm run dev` перед тестами.
Тесты используют настоящий браузер и настоящий IndexedDB — никакого
mock DOM. Файлы: `dashboard.spec.ts`, `editor.spec.ts`,
`persistence.spec.ts`, `templates.spec.ts`, `images.spec.ts`,
`responsive.spec.ts`. Фикстуры изображений — реальные PNG-файлы в
`qa/runtime/fixtures/`.

### Required environment

- Node ≥ 18.18 (указано в `package.json` → `engines`)
- npm ≥ 10
- доступ к registry.npmjs.org (для `npm install`)
- Chromium для Playwright (`npx playwright install chromium`)

**Эти тесты подготовлены, но НЕ запускались** — песочница, в которой
велась разработка, не имеет доступа к npm registry
(`HTTP 403 host_not_allowed` от egress-прокси; см. отчёт шага 9).
Не считайте написание этих тестов доказательством прохождения
runtime QA — это доказательство только после реального
`npm run qa:runtime` на машине с сетью.
