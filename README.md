# КОБОЛЬТ-Б

Конструктор внутреннего боевого листка танкового батальона.
Next.js (App Router) + TypeScript + Tailwind CSS.

## Статус: шаг 2 вертикального слайса (визуальная обложка)

готов, без изменений.

  (210×297mm) в одном месте;

  страницы выпуска; и Preview, и будущий `/api/pdf` (шаг 5) рендерят

  `HeroMedia`, `ContentsBlock`, `EditorialRule`. `CoverV1.tsx` их

Дизайн-принцип, зашитый в компоненты: `ContentsBlock` и `HeroMedia`
показывают ровно то, что есть в `Issue` — без выдуманного текста;
если материала мало, остаётся пустое пространство (плюс фоновая
гравюра как композиционный якорь), а не placeholder-заполнение.

1. Template B при единственном абзаце: фиксированная раскладка в 2

2. Template B при 5 фотографиях + большом объёме текста: сетка фото

   фиксированного бюджета высоты — проверено программным замером
   `scrollHeight` относительно `clientHeight` страницы, переполнение
   устранено (0мм на всех шести проверенных состояниях).

Решение по автомасштаблированию (принято, не реализовано): при
переполнении контента страница НЕ должна ломаться, обрезаться или
уменьшать шрифт до нечитаемого размера. Целевое поведение — состояние
"Материала слишком много для выбранного шаблона. Выберите другой
шаблон или сократите материал". Сам механизм намеренно отложен.

## Архитектура PDF (согласовано, реализация — на шаге 5)

Клиент сериализует весь `Issue` (JSON, включая base64/data-URL фото) и
отправляет его целиком в `POST /api/pdf`. Сервер не обращается к
IndexedDB — он ничего не знает о выпуске, кроме присланного тела
запроса. Роут рендерит **тот же** React-компонент `A4Page`, что и
Preview в браузере (через headless Chromium), — разметка не
дублируется. Для запуска Chromium в serverless-функции Vercel
используется `puppeteer-core` + `@sparticuz/chromium` (обычный полный
`puppeteer` превышает лимит размера serverless-функции на Vercel);
альтернатива при необходимости — вынести рендер в отдельный сервис
(например, Browserless) и обращаться к нему по HTTP из `/api/pdf`,
если потребуется больше 50 сек. на функцию.

## Статус: PDF export, Content Zones / Editor Guides, UI cleanup (текущий этап)

Реализовано в порядке, зафиксированном в ТЗ этого этапа:

### PRIORITY 1 — `/api/pdf`

- `app/api/pdf/route.ts` — `POST`, Node.js runtime, принимает полный
  `Issue` JSON в теле запроса, ничего не читает из IndexedDB (сервер о
  ней просто не знает).
- `lib/pdf/renderIssueHtml.tsx` — рендерит **тот же** `A4Page`
  (`react-dom/server`), что и живой Preview, четыре страницы подряд в
  одном HTML-документе с `page-break-after: always` между ними — один
  вызов `page.pdf()` даёт ровно 4 физические страницы без склейки
  через сторонние библиотеки.
- `lib/pdf/buildTailwindCss.ts` — компилирует настоящий Tailwind CSS
  (те же токены цвета/радиусов/шрифтов, что в `tailwind.config.ts`)
  под контент конкретно этого HTML, а не читает файл сборки `.next` —
  надёжнее в serverless-окружении и не зависит от хеша имени файла.
- `lib/pdf/googleFonts.ts` — Oswald/PT Sans встраиваются как base64
  `@font-face` (тот же источник, из которого их берёт `next/font` на
  этапе сборки Next.js), поэтому сам рендер PDF не зависит от сети.
- `lib/pdf/launchBrowser.ts` — на Vercel (`process.env.VERCEL`) —
  `puppeteer-core` + `@sparticuz/chromium`; локально — `puppeteer-core`
  + путь к уже установленному Chromium через `PUPPETEER_EXECUTABLE_PATH`
  (см. "Required environment" ниже).
- Кнопка **"Скачать PDF"** (`components/editor/DownloadPdfButton.tsx`)
  — в `EditorTopBar`, видна и на desktop, и на mobile. Перед запросом
  проверяет `overflowingPages` (см. ниже) — если хоть одна из 4
  страниц физически не помещается в свой шаблон, PDF не запрашивается,
  вместо этого показывается политика overflow.
- Имя файла: `kobolt-b-vypusk-{issueNumber}.pdf`.

### PRIORITY 2 — семантика контента

Проверено против уже реализованной (в предыдущем этапе) модели
`H1 → H2 → лид → абзацы → достижения/спецэлементы → цитата`
(`lib/content/types.ts`, `pageBlocks.ts`, `sections.ts`) — стабильные
`titleId`/`subtitleId`/`leadId`/`quoteId` сохраняются, регрессии не
внесено. Изменений в этой части в текущем этапе не потребовалось.

### PRIORITY 3 — Editor Content Zones / Guides

- Каждый шаблон (`components/templates/**`) помечает свои смысловые
  контейнеры атрибутом `data-zone="h1|h2|lead|paragraph|photo|caption|
  quote|achievement"` — сам атрибут ничего не стилизует и присутствует
  везде, включая PDF (безвредная метка, не CSS).
- `components/editor/guides/ContentZoneOverlay.tsx` — считывает эти
  `[data-zone]` элементы из реального DOM (геометрия — из
  offsetTop/Left/Width/Height относительно `.kobolt-page`, не зависит
  от масштаба `PagePreviewScaler`), рисует тонкие пунктирные рамки +
  мелкие подписи (H1/ТЕКСТ/ФОТО/…). Монтируется **только** в
  `app/issues/[issueId]/page.tsx` (редактор) — ни в `/preview`, ни в
  `/api/pdf` этот компонент не импортируется вообще.
- Page-level overflow (сравнение `scrollHeight`/`clientHeight`
  `.kobolt-page`) показывает баннер с точной политикой
  "Материала слишком много для выбранного шаблона. Выберите другой
  шаблон или сократите материал." прямо в preview редактора.
- `components/editor/guides/HiddenOverflowProbe.tsx` — тот же принцип
  измерения, но для всех 4 страниц разом (не только активной) —
  результат уходит в кнопку "Скачать PDF".

## Runtime QA

Этот проект требует **сети** (npm registry) и **Chromium** (для
Playwright), которых нет в среде, где готовился этот код. Ниже —
единственный подтверждённый способ провести реальную runtime-проверку.

### Install

```bash
npm install
```

`package-lock.json` в репозитории намеренно отсутствует — он должен
быть сгенерирован здесь, на машине/CI с доступом к registry. Ручной,
"нарисованный" lockfile не создавался: `npm ci` в CI-workflow
(`.github/workflows/qa.yml`) будет падать до тех пор, пока
получившийся `package-lock.json` не закоммичен в репозиторий.

### Development

```bash
npm run dev
```

### Runtime tests

```bash
npm run qa:runtime
```

Запускает `qa/runtime/*.spec.ts` через Playwright на трёх вьюпортах
(1440×900, 1024×768, 390×844 — см. `playwright.config.ts`), с
`webServer`, который сам поднимает `npm run dev` перед тестами.
Тесты используют настоящий браузер и настоящий IndexedDB — никакого
mock DOM. Файлы: `dashboard.spec.ts`, `editor.spec.ts`,
`persistence.spec.ts`, `templates.spec.ts`, `images.spec.ts`,
`responsive.spec.ts`. Фикстуры изображений — реальные PNG-файлы в
`qa/runtime/fixtures/`.

### Required environment

- Node ≥ 18.18 (указано в `package.json` → `engines`)
- npm ≥ 10
- доступ к registry.npmjs.org (для `npm install`)
- Chromium для Playwright (`npx playwright install chromium`)
- для реального PDF-QA (`qa/runtime/pdf-export.spec.ts`) — тот же или
  любой другой Chromium, доступный `/api/pdf` в режиме разработки:
  установите переменную окружения `PUPPETEER_EXECUTABLE_PATH`,
  указав на бинарник (например,
  `~/.cache/ms-playwright/chromium-*/chrome-linux/chrome` после
  `npx playwright install chromium`), либо системный
  `google-chrome`/`chromium`. Без неё `/api/pdf` в dev-режиме вернёт
  понятную ошибку "не найден исполняемый файл Chromium" вместо PDF —
  это ожидаемо и не является багом (см. `lib/pdf/launchBrowser.ts`).
  На Vercel эта переменная не нужна — там используется
  `@sparticuz/chromium` автоматически.
- сеть до `fonts.googleapis.com`/`fonts.gstatic.com` при первом вызове
  `/api/pdf` в тёплом инстансе (встраивает Oswald/PT Sans как base64;
  см. `lib/pdf/googleFonts.ts`) — при недоступности сети PDF всё равно
  сформируется, но шрифтами лягут системные fallback (Arial Narrow/
  Arial), а не Oswald/PT Sans.

**`package.json` в этом этапе изменился** (`tailwindcss`/`postcss`/
`autoprefixer` перенесены из `devDependencies` в `dependencies` —
нужны в рантайме `/api/pdf`, не только на билде; добавлены
`puppeteer-core`, `@sparticuz/chromium`, `pdf-parse`) — существующий
`package-lock.json`, если он уже был закоммичен после прошлого этапа,
**рассинхронизирован** с новым `package.json`. Перед `npm install`/
`npm ci` в CI это нужно перегенерировать:

```bash
rm -f package-lock.json
npm install
```

и закоммитить получившийся `package-lock.json`.

**Эти тесты (включая новые `content-zones.spec.ts` и
`pdf-export.spec.ts`) подготовлены, но НЕ запускались** — песочница, в
которой велась разработка этого этапа, не имеет доступа к npm registry
(`registry.npmjs.org` не в allowlist сетевого прокси; проверено
`curl`/`npm install`, тот же класс ограничения, что и в отчёте шага 9).
Не считайте написание этих тестов или чтение исходного кода
доказательством прохождения runtime/PDF QA — это доказательство
только после реального `npm run qa:runtime` (и ручной проверки кнопки
"Скачать PDF") на машине с сетью.

## Реальная production-QA PDF-экспорта — выполнена (Vercel, kobolt-b.vercel.app)

В отличие от прочих runtime-тестов выше, **этот пункт был проверен по-настоящему** —
не в песочнице разработки (без доступа к npm registry), а на реальном
production-деплое на Vercel, вживую, с реальным Chromium и реальным
скачиванием файла на телефоне.

По пути было исправлено несколько реальных ошибок, которые вскрылись
только на настоящей сборке/рантайме Vercel (ни одна не была видна
статическим анализом кода в песочнице разработки):

1. **`bd73096`** — Next.js App Router запрещает статический
   `import ... from "react-dom/server"` в любом файле, достижимом из
   `app/` (даже в обычном Route Handler). Исправлено на динамический
   `await import("react-dom/server")` внутри функции.
2. **`63f38b6` → `e987ca2`** — сборка (`next build`, SWC) падала с
   `Syntax Error` именно в `lib/pdf/launchBrowser.ts`; убрать обратные
   кавычки из текста ошибки не помогло (ошибка просто "уехала" дальше
   по файлу) — помогло только полностью переписать комментарии и текст
   ошибки в этом файле на простой ASCII/английский вместо плотной
   кириллицы с тире/стрелками. Похоже на баг парсера SWC на Vercel,
   специфичный именно для этого файла — граница ещё не выяснена точно,
   но фикс воспроизводимо устранил ошибку сборки.
3. **`44acb8a` → `3b742d4`** — сборка прошла, но реальный вызов
   "Скачать PDF" падал в рантайме: `Failed to launch the browser
   process! /tmp/chromium: error while loading shared libraries:
   libnss3.so: cannot open shared object file`. Попытка форсировать
   `experimental.outputFileTracingIncludes` не помогла сама по себе.
4. **`ffee112` → `4e8b4ce`** — настоящая причина: версии
   `@sparticuz/chromium` до 141.x определяют Lambda-совместимое
   окружение только по переменным окружения настоящего AWS Lambda,
   которых Vercel не выставляет, поэтому распаковка Chromium и его
   системных библиотек (включая `libnss3.so`) никогда не запускалась.
   Обновили пакет на `^141.0.0` + добавили защитный fallback
   `process.env.AWS_LAMBDA_JS_RUNTIME ??= "nodejs22.x"`
   (`lib/pdf/launchBrowser.ts`). Заодно у 141.x убрали
   `chromium.defaultViewport` — пришлось убрать использование этого
   поля (`4e8b4ce`, это уже настоящая ошибка типов TypeScript на
   сборке, не гипотеза).

**Результат реальной проверки (подтверждено пользователем на
kobolt-b.vercel.app, выпуск №7, 26 сентября 2026):**

- Сборка на Vercel — **успешна** (коммит `4e8b4ce`).
- Кнопка "Скачать PDF" — реально скачивает файл, имя файла
  соответствует шаблону `kobolt-b-vypusk-{номер}.pdf`
  (`kobolt-b-vypusk-7.pdf`).
- Файл открывается как настоящий PDF (проверено во встроенном
  PDF-просмотрщике Chrome на Android).
- Ровно **4 физические страницы** — без лишней 5-й пустой.
- Формат страниц — портретный A4.
- Страница 1 (обложка) отрендерена **полностью и корректно**: фон,
  типографика, оглавление, силуэт танка — совпадает с live-превью.
- Страницы 2-4 в этой проверке пустые — это ожидаемо: пользователь не
  назначал им шаблон/контент в этом тестовом выпуске (не баг
  PDF-экспорта, а отражение реального состояния выпуска — так же
  пусто и в live-превью для этих страниц).

**Ещё не проверено по-настоящему** (см. TODO ниже) — overflow-баннер на
реальной сборке, Content Zone guides в редакторе на реальной сборке,
мобильная регрессия (390×844) на реальном устройстве,
персистентность/переключение шаблонов на реальной сборке. Это
следующий шаг QA.

### Обновление: страницы 2-4 с реальным контентом + фикс ошибки 413

Повторная проверка с реальными фото на всех 4 страницах (не только
обложка) вскрыла ещё одну реальную production-ошибку:

5. **`2b265e4`** — при реальных фото на нескольких страницах кнопка
   "Скачать PDF" стала возвращать `Сервер вернул ошибку 413`
   (Payload Too Large). Причина: Vercel Serverless Functions имеют
   жёсткий потолок ~4.5 МБ на тело запроса (ограничение платформы, не
   настраивается через `next.config.js`), а фото в IndexedDB и,
   соответственно, в отправляемом на `/api/pdf` JSON выпуска хранятся
   в полном разрешении как data URL — с несколькими реальными фото это
   легко превышает лимит. Добавлен `lib/pdf/prepareIssueForPdf.ts`:
   перед отправкой на `/api/pdf` фото крупнее ~300КБ уменьшаются до
   1600px по длинной стороне и перекодируются в JPEG (качество 0.82);
   IndexedDB и live-превью используют оригиналы без изменений — сжатие
   применяется только к копии, уходящей в этот один запрос.

**Подтверждено пользователем на реальном выпуске (все 4 страницы, с
реальными фото на каждой странице, kobolt-b.vercel.app):**

- PDF успешно скачивается без ошибок (413 больше не воспроизводится).
- Ровно 4 страницы, все с реальным содержимым (фото на всех 4).
- Пустые серые поля "текст статьи" на страницах 2-3 — ожидаемо: в этом
  тестовом выпуске были заполнены только фото, без текста абзацев.
- Небольшая обрезка фото-коллажа на странице 4 рамкой фото — это
  обычная `object-fit`-обрезка фото под размер рамки, не переполнение
  страницы; пользователь явно подтвердил, что вёрсточная точность
  фото/отступов сейчас не в фокусе проверки ("я не смотрю на вёрстку
  строго, только функционал") — это совпадает с ранее отложенными
  пунктами ТЗ (полная вёрсточная полировка A4, идеальный подбор
  размеров фото).
